What does MNDe actually do?

MNDe is an execution boundary: it validates a request, computes a deterministic ALLOW or REFUSE decision, and only then executes or refuses. The decision happens before any cost is incurred, not after.

See the pipeline

Why are decisions deterministic?

The same input always produces the same decision and the same hashes, because the decision is a pure function of the request and a versioned policy. Nothing depends on timing, ordering, or runtime.

Run the determinism test

Is the decision made in my browser?

No. The browser only sends inputs and renders the response. Every ALLOW/REFUSE decision is computed server-side by /api/simulate and returned with a request and decision hash.

What is in the proof bundle?

A ZIP with a manifest, drift report, parity report, replay report, and a sample decision. Its SHA-256 is published so you can confirm the file you downloaded is the one described.

What happens when I submit the contact form?

Your request is validated and sanitized, then queued and routed for review, returning a real request ID and timestamp. If mail is not configured or sending fails, you get an explicit error — never a fake success.

Is MNDe production-ready?

Not yet, and we say so. MNDe is pre-1.0: v1.0 is not tagged, and finding F-001 (replay-safe, single-use authority in production) is not closed. The reference implementation is built and tested; the first typed production effect, git.push, has not yet been operated end to end with production trust.

Read the status

What does ALLOW mean?

That policy approved the request. It never means the action ran, and outside the typed git.push path it does not authorize execution: generic protected execution is on hold, and decision receipts say so in their signed body.

See what is on hold

What is the first production effect?

git.push. MNDe moves one branch on one remote from one exact commit to another, using an argv it builds itself with --force-with-lease, no shell, and no caller-supplied flags. Every field must match the signed authorization, the authority is consumed once in a durable claim store, and signed evidence reports EXECUTED only if the remote reads back the approved commit.

See the git.push contract

What happens if the power fails?

Restart recovery is tested; power loss is a documented known limitation for v1.0, not a closed question. In production, sustained power continuity (a UPS or generator) is the operator's responsibility, outside MNDe.

Read the known limitations

Can MNDe verify my GitHub branch protection offline?

No. Branch protection and required reviews live in GitHub's settings, outside MNDe. MNDe does not produce a receipt for them and does not claim to verify them offline. Its offline verification covers its own receipts and evidence.
