Replay defense · 2026-07-17

Single-use by default: authority that cannot be replayed

A grant that can be presented twice is a grant you have already lost control of. If authority survives its own use, then leaking it once leaks it forever. The defense is structural: one nonce, one action, consumed exactly once.

Reusable credentials are the default almost everywhere, and they are the reason a single leaked secret is so catastrophic. A token, an API key, a signed URL — each is designed to be presented as many times as needed. That reusability is convenient and, for authorization, dangerous. It means the value of stealing the credential is not one action; it is every action the credential permits, for as long as it lives.

Replay is the cheapest attack there is

Replay requires no cleverness. Capture a valid request and send it again. If the authority attached to that request is reusable, the second send is as good as the first. Retries, at-least-once delivery, and duplicated messages produce the same effect by accident: the same authorized action executes more than once. Whether the duplication is malicious or a distributed-systems artifact, the failure mode is identical, and a reusable grant cannot tell them apart.

One nonce, one action, consumed once

Single-use authority removes the premise. Each grant carries a single-use nonce. Before the protected executor acts, it atomically reserves and consumes that nonce in a consumption ledger. The first presentation wins the reservation and proceeds; every later presentation of the same nonce loses the race and is refused as replay. The grant is spent by being used. There is nothing left to steal, resend, or duplicate.

This also gives duplicate delivery a clean answer. A message delivered twice presents the same nonce twice; the second consumption is refused, and the action happens once. Exactly-once execution stops being a property you hope the network provides and becomes a property the authority enforces.

Authority is spent when it is used: a nonce reserved once cannot be reserved again, so a grant presented a second time is refused, not honored.

What "single-use" requires to be true

The guarantee is only as strong as the ledger that enforces it. Consuming a nonce exactly once, even when many presenters race concurrently, is a linearizability problem. A browser demonstration can show one-winner selection as a reference, and that reference is implemented — but a demo does not prove distributed correctness. In MNDe the consumption ledger is a limited component today: the reservation semantics are defined and enforced in the reference, while a production-grade, highly available ledger with a verifiable consumption history is target architecture. Distributed proof requires a deployed ledger, and we do not claim it before that exists.

Fail-closed behavior matters here too. If the ledger cannot complete a reservation, the correct outcome is refusal, not a hopeful execution. An authorization system that degrades to "allow" under partition has inverted its own purpose. Single-use authority that cannot confirm consumption must decline to act.

The payoff

Once authority is single-use, the economics of a leak change completely. A captured grant is worth, at most, one action that was already authorized — and only if it has not already been consumed and has not expired. The standing prize that makes credential theft worthwhile simply is not there.
