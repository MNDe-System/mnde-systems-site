Capability, not identity, is the unit of machine trust

Identity answers one question: who is asking. It was never designed to answer the question that actually protects a system — is this exact action, on this exact resource, right now, authorized.

Most access control still assumes a person sits behind every request. A human logs in, we authenticate them, and we lean on judgment, latency, and consequences to keep the blast radius small. The account is the principal, and the account maps to someone who can be held responsible. That assumption is quietly dissolving. The principals making consequential requests are increasingly agents: software that plans, calls tools, and acts thousands of times faster than any reviewer.

Identity is a claim about the requester, not the request

An identity token proves an actor is who it says it is. It says nothing about scope. A valid token for a service that is allowed to merge pull requests is equally valid for merging the right pull request and the wrong one. The moment we grant a broad identity a broad permission, every future action taken under it inherits that breadth — including actions no one anticipated when the permission was issued.

For a human operator this is tolerable, because a person rarely exercises the full surface of what they are technically allowed to do. An agent will. It explores the permission surface exhaustively and without hesitation, because that is what optimization looks like. Identity-shaped controls degrade precisely when the actor stops being a person.

Capability is a claim about the action

A capability inverts the question. Instead of "is this actor allowed to do things of this kind," it asks "does this actor hold valid, specific, unconsumed authority for exactly this action." The authority is not a role the actor is; it is an object the actor must present, bound to a single action, a single resource, a canonical set of parameters, and a short lifetime.

In MNDe this object is an exact-action grant. It is not a session and not a role. It names one operation and refuses to stretch to cover a neighboring one. If any bound field changes — the repository, the commit, a parameter — the grant identity changes and verification fails before the protected executor contacts any provider.

The unit of trust is the authorized action, not the authenticated actor: no consequential action executes without valid, specific, unconsumed authority for that exact action.

What this does and does not claim

Capability-based authority does not abolish identity. The authority plane still needs to know who is requesting a grant, and delegation still starts from an authenticated principal. The claim is narrower and more durable: identity should decide whether you may obtain authority, and a capability should decide whether a specific action executes. Collapsing those two decisions into one long-lived permission is the mistake.

It is worth being precise about maturity. Canonical parameter binding — the mechanism that makes a grant refer to one action and not its neighbor — is implemented and runs as a reference in the browser. Non-bypassability, the property that an agent cannot simply route around the grant and call the provider directly, is target architecture: it depends on provider identity, credential custody, and network policy, and it is only real once a deployment enforces it. We say so rather than implying the end state already holds.

Why the shift is not optional

The trajectory is one-directional. The number of non-human principals in a typical system is growing, and each one is faster and more literal than the humans it replaces. Controls that key off identity were tuned for a population that no longer dominates the request stream. Keying trust to the action — the thing that actually has consequences — is how authorization survives that shift.
