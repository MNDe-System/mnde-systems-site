What is built, what is proven, what is open.

MNDe is pre-1.0. This page separates three things that are easy to blur: code that exists and is tested, properties demonstrated against real infrastructure, and questions that are still open. The engineering records behind it are linked throughout.

Built and tested

In the reference implementation today.

Source: MNDe-System/mnde-public-test. Pure Node.js (24+), zero runtime dependencies, CI on Windows with SHA-pinned actions.

Implemented / Reference

Decisions and signed receipts

A caller submits an action before running it. MNDe returns ALLOW or REFUSE and writes an Ed25519-signed receipt that verifies offline against a trust anchor. An ALLOW means policy approved the request; it never means the action ran.

Implemented / Reference

Typed git.push effect

Moves one branch on one remote from one exact commit to another, only when a signed authorization says so. MNDe builds the argv itself; there is no shell and no caller-supplied flag or refspec.

Implemented / Reference

Signed execution evidence

A separate evidence record, signed by the executor's own key, reports EXECUTED only when the remote ref read back after the push equals the approved commit. It is a different schema from the decision receipt, so neither can stand in for the other.

Implemented / Reference

Production posture gate

With MNDE_PROFILE=production, the executor refuses to start unless an authority bundle, a pinned root fingerprint, an executor id and an environment id are configured. It never falls back to the demo authority.

Implemented / Reference

Executor-owned push credential

The executor obtains its own push credential, scoped to an allowlist of repositories, and hands it only to the git processes that talk to the remote. The caller never sees it.

Limited

Generic execution is on hold

Outside the typed git.push path, protected execution is disabled in the executor and the MCP proxy. Decision receipts say so in their signed body (execution_status: "DISABLED").

Proven against real infrastructure

Single-use authority, measured on a real database.

The claim store that makes an authorization single-use was run against PostgreSQL 16.13 with fsync on, verified TLS, and a restricted non-owner login.

What this does not establish: it does not close F-001. Restart is not power loss. No managed database provider and no failover were tested. "The executor cannot roll the claim store back" is not "nobody can": whoever owns the database can restore a backup. Read the full proof record.

F-001 · the nine questions

Can one authorization cause more than one effect?

F-001 is the finding that blocks a production execution claim. It is assessed as nine questions against the real git.push path. Six are established; it is still not closed, because a correct design that has never been operated end to end with production trust is not a closed finding.

Open, stated plainly

Known limitations.

No production run yet

The git.push path has not been operated end to end with production trust material against a production remote. That run is the blocker that moves F-001.

Power loss

A documented known limitation for v1.0, not a closed question. Restart recovery is tested; a disk that lies about flushing is not. Sustained power continuity in production is the operator's responsibility (UPS, generator) outside MNDe.

Database restore

The executor cannot roll its claim store back. A database owner can restore a backup and revive spent authority. Restore and admin authority must sit outside the automated system. An external monotonic witness is planned for after v1.0.

Non-bypassability depends on deployment

MNDe cannot stop an action that is never submitted to it. If another valid credential exists outside the executor, the boundary can be walked around. The repository host's permissions must make the executor the only path.

Repository settings are not offline-verifiable

Branch protection and required reviews live in GitHub settings, outside MNDe. MNDe does not produce a receipt for them and does not claim to verify them offline.

No published authority bundle

Offline verification works against a trust anchor today, but a stable, MNDe-published authority bundle for verification outside the repository does not exist yet.

What we will not say

Claims this site is built to avoid.

  • “F-001 is closed.” Not yet, and not for effects other than git.push on this evidence.
  • “Nobody can roll the claim store back.” Only the executor cannot.
  • “ALLOW means it ran.” A decision never implies execution occurred or is permitted.
  • “MNDe verifies your GitHub settings offline.” It does not.
  • “Production verified.” Reserved, and currently unused anywhere on this site.
